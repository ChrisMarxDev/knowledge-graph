A cleaner, more ordered knowledge graph

Borrow Graphify’s visual hierarchy; preserve kw’s knowledge semantics.

Planned feature index

2 · Scope and constraints

Goal: make the map readable as an overview, with titles and relationship details available when investigating a node. Keep ordinary knowledge reading and navigation intact.

  • Keep Cytoscape initially. Keep type colors stable across Graph/List, views, filters, and the reader.
  • Keep one visible node per document in ordinary Graph mode. Never generate or write links to make the picture look connected.
  • Keep metadata filters, saved views, unresolved-link diagnostics, List accessibility, source navigation, and the existing pan/Command-scroll gestures.
  • No CLI, storage format, graph API, inference model, or server dependency change is required for the first two phases.
  • Grouping, reduced decoration, and collapsed summaries are proposed behavior changes. No explorer code is changed by this plan.

3 · Baseline before implementation

  1. Capture reproducible screenshots with the same viewport, light/dark theme, camera fit, and saved-position state. Compare the same node/edge data, not two different codebases.
  2. Use this 25-node hub graph, the 20-node/41-edge explorer example, a two-node graph, and synthetic fixtures with disconnected nodes, long titles, dense parallel links, and 250/1,000 nodes. Synthetic data is a performance fixture, not claimed user scale.
  3. Measure visible label overlaps, node overlaps, crossings (trend only), occupied area, layout duration, and the ability to locate a named node and trace one relationship.
  4. Compare new settings against current fCoSE before evaluating ForceAtlas2. Preserve baseline screenshots so “cleaner” is reviewable.

4 · Phase 1 — Reduce simultaneous detail

Implemented first pass — awaiting visual review. Uniform 24px nodes, zoom-based title density with collision checks, persistent dimension markers, and quieter edges are built. Background and layout changes remain deferred. The implementation notes below retain the original design scope. Zoom controls how much information is visible. Preserve dimension markers as navigation cues and try small, uniform nodes. Change presentation without moving nodes first, so its effect can be judged separately.

Change Technical step Result / guardrail
Adaptive labels Add ui/graph-presentation.ts to select labels by zoom and screen-space collision boxes. Prioritize selected/hovered node, visible neighbors when focused, search hits, then a bounded set of connected nodes. Stable path/ID tie-breaker. For small sparse graphs, keep all labels that fit. For crowded overviews, show fewer labels. Selected/hovered titles remain available; List and hover expose all names. No arbitrary top-degree-only cutoff.
Quieter glyphs Trial small, uniform visual diameters within 12–24px. Keep node sizes stable across filtering and selection. Connection count should not imply importance. Do not resize/recolor nodes when filtering. Resolve easy selection through hover/zoom and List; test pointer targeting.
Dimension accents Keep dimension markers visible, including at overview zoom. Preserve their identities and colors in the graph and cards/reader. Check legibility with the smaller node bodies. Christopher uses dimensions to recognize and find important nodes. Zoom-based simplification must preserve these cues.
Edges Trial width 0.6–0.9px and opacity 0.2–0.35; emphasize selected neighborhood. Show clear arrowheads and relation labels for focused edges. Reduce overview arrow prominence; keep an explicit all-directions option if needed. Do not remove authored edges. Current edge labels already appear only on focus; retain that. Keep missing-section/unresolved styling distinguishable.
Canvas Compare a plain background with the existing dotted grid; reduce nonessential visual texture. Keep light and dark themes. Graphify’s dark screenshot is not a requirement to force dark mode.

5 · Phase 2 — Improve spacing and preserve orientation

Implemented trial: fixed 48px collision footprints, 12000 repulsion, degree-adjusted spring length and attraction, unique endpoint pairs for layout, and disconnected-component packing with 90px gaps. Explicit Tidy applies the trial to saved graphs. Visual acceptance, incremental placement, and large-graph benchmarks remain open.

Change Technical step Result / guardrail
Decouple layout from transient labels Pass stable node-body/collision dimensions to the worker; perform label placement in screen space. Add bounded padding for detail labels rather than reserving every full wrapped title. Zooming and label reveal must never trigger a force layout. Avoid layout density that makes detail labels impossible.
Pack disconnected components Compute components; lay each out, then pack their bounds with fixed gaps. Treat isolated nodes as a compact, selectable region. Verify whether fCoSE packing needs an extension before adding any dependency. packComponents=false is an existing limitation, but not the cause of this connected 25-node graph. Do not simply flip a flag and assume packing works.
Handle hubs and parallel links Compare equal springs with degree-normalized attraction. Deduplicate parallel endpoint pairs for layout forces only; retain every authored edge in rendering/details. No hardcoded relation names or ontology. A heavily linked project node must not collapse all other concepts into one center.
Stable positions Use sorted stable inputs and existing positions; persist versioned layout settings. Explicit Tidy runs the new arrangement; filter/search/metadata updates preserve existing node positions. Current code may rerun layout when new nodes are added: test and constrain this. Newly added nodes start near existing neighbors; fall back to deterministic placement if isolated.
Engine decision Benchmark fCoSE configurations first. Only prototype ForceAtlas2 with the same fixtures if overlap/cluster separation targets remain unmet. No renderer rewrite merely to match a screenshot. Keep cancellation, worker isolation, and camera behavior.

6 · Phase 3 — Optional spatial groups

Only after Phase 1–2 review. Graphify uses community colors; kw already has an accepted meaning for node colors. Use space and subtle group headings, not automatic recoloring.

Change Technical step Result / guardrail
Connected structure Derive temporary topology groups only from authored resolved edges. Test community detection on fixtures; name derived groups conservatively. Sparse/star graphs may not contain useful communities. Do not imply algorithmic groups are authored facts.
Authored dimensions Allow an explicit Group by dimension choice, e.g. feature, only when the user selects it. Unspecified and multiple-membership nodes get explicit handling. Choose one primary spatial placement with visible membership detail; do not duplicate a node into several groups or silently drop memberships.
Group layout Lay out each group internally, pack groups with gaps, then route cross-group relationships. Use very light boundary/heading treatment, not another multicolor encoding. Preserve node type colors. Grouping is reversible browser presentation state; filters and saved views still mean selection, not automatic clusters.

7 · Phase 4 — Large-graph overview, only if needed

When measured scale makes individual nodes unusable, add an explicit group-summary mode. Summary nodes carry counts and expand to the existing document graph; summary edges carry counts of underlying authored links. Always indicate the mode and visible/total counts. Do not automatically hide documents, randomly sample edges, or silently turn a view into an aggregation. Defer until a real collection or fixture demonstrates need.

When implementation ships, synchronize the explorer sections of the usage skill, CLI/API knowledge node, README and human docs. This plan itself does not amend the implemented contract or the stable-color decision.

9 · Acceptance and rollout

  • At baseline overview: zero overlapping visible labels on small fixtures; at scale, collision suppression reduces label density while focus labels remain discoverable. Measure actual collisions; do not claim a result before testing.
  • All nodes remain reachable via Graph/List/search; all authored connections remain inspectable, including direction and relation.
  • No node moves on zoom, hover, selection, theme changes, or label visibility changes. Filtering must restore previous positions when cleared.
  • Group or layout changes happen explicitly. Fit changes camera only; Tidy changes positions. Reader opening preserves the graph workspace geometry as today.
  • Worker cancellation still works; target <2s arrangement for 250 nodes and <5s for 1,000 on the measured development machine. These are proposed acceptance targets, not measured performance guarantees.
  • Inspect same-data before/after screenshots in both themes at 1280×800 and a narrow viewport. Validate hover, selection, long labels, keyboard-accessible List, and non-color focus cues.
  • Ship/review Phase 1 separately, then Phase 2. Approve grouping only after seeing whether those already solve the problem.

Scores are planning estimates. Agreed choices: zoom-based detail, small uniform nodes for the first trial, and visible dimension markers at overview zoom. Open visual choices: title density at overview; whether direction arrows should remain faintly visible everywhere; and whether a grouping control is needed at all. Recommendation: start with adaptive labels, simpler dots and quiet edges, then review screenshots before choosing groups or a new layout engine.
